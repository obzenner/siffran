# Testing and native qualification

The Makefile has three deliberately separate layers. None is a substitute for another.

## Fast contributor gate

`make check` runs the fast suites in parallel through `scripts/run_suites.py`; every suite runs. The next queued suite starts only while the 1-minute load average is below `RUN_SUITES_MAX_LOAD` (default: the CPU count), and when nothing is running one suite always starts, so a busy machine slows the run but never stalls it. The queue is longest first, from each passing suite's previous wall time (`RUN_SUITES_DURATIONS`, default `run-suites-durations.json` in the system temporary directory; a suite with no recorded time starts first). `make check JOBS=<n>` (also `check-ci`) caps the suites running at once, default none; an invalid `JOBS` or `RUN_SUITES_MAX_LOAD` is refused. Each suite's output goes to its own log in a fresh temporary directory (the path is printed), with one status line per suite and its elapsed time; a failed suite's log is printed in full the moment it fails, and any failed suite fails the run. The suites are the Makefile's `FAST_SUITES`.

Each suite runs in its own process group, and the runner tracks every launched group until it has cleaned it up, even after the suite's leader process has exited. A suite's limit is declared with the suite, `NAME@SECONDS='COMMAND'` (for example `check-observer@900=...`); a suite that declares none has `RUN_SUITES_TIMEOUT` seconds (default 600). Both must be a finite positive number of seconds: `0`, a negative, `nan`, `inf`, a non-number or an empty `NAME@=` is refused before anything starts. A suite that runs longer than its limit is stopped and fails with a `timed out after N s` line. Stopping is the one process-group owner that `scripts/run_suites.py` and `scripts/verify.py` share (`run_suites.Groups`): each group it starts gets a folder in its registry, and the group's processes inherit `RUN_SUITES_GROUPS` naming it, so a runner started inside a suite or a `make verify` step (`check` runs `run_suites.py`) registers its own groups below it, although they leave its process group. A stop first asks: SIGTERM to the group and every group registered below it, waiting up to a 5 s grace for them to empty (the nested runner cleans up its own groups then); then SIGKILL to every registered group and the group itself, always, even when the leader already exited after SIGTERM, so a descendant that ignores SIGTERM dies too. A registration is removed only once its group is empty, before its leader is reaped, so a listed group id stays pinned until cleanup finishes. When the suites finish, fail, time out or are interrupted, every launched group is stopped that way; the leaders are reaped, and the runner checks that every group is empty (a group it cannot empty fails the run, and stays registered for an outer runner). The first SIGINT or SIGTERM stops the run; later signals are deferred and cannot interrupt cleanup. The runner prints "every suite was stopped" only after that check passed, and exits 130 or 143 after an interruption. Every suite is also a `make check-<suite>` target that runs on its own. Each test module belongs to exactly one fast suite, or to a named integration target (`scripts/tests/test_suite_ownership.py` takes the suite names from `FAST_SUITES`, reads each suite from `make -n`, resolves every module and path selection against that command's own working directory, and compares repository-relative paths, so a same-named file elsewhere never counts as owned; it fails on an unowned or doubly owned test file, and its exception list is empty). `make check-ci` runs the same runner over static, core, evidence, observer, Claude and Codex, and adds Pi and UI with `PI_CHECKS=1` (`check-ui` needs Node, like Pi); `make test` aliases `make check`. Missing Node/TypeScript tooling fails unless `EMPIRICA_ALLOW_SKIP=1` explicitly acknowledges the omission. Tests that read `node_modules` (the pinned pi-subagents inventory, preflight, and parameter-schema checks in `make pi-auditor-resolution-unit-check`) live in the Pi suite so the Node-free core suite that CI runs stays Node-free; `make empirica-identity-pi-levels-check` reads only the contract's `thinking_levels` and a shared fixture, and needs no Node.

## Targeted integration diagnostics

The application, capability-authority, local-image-resolution, pure compiler, semantic-admission,
immutable staging, bounded-effects, reconstructing-journal, cleanup/recovery, and one-container
harness and five-probe qualification checkpoints are complete. Qualification and installation are
separate Make-owned operator operations: the first writes only a private candidate, and the second
revalidates current implementation, semantic capability, profile, and candidate identity before
atomically publishing the new `/2` record and pointer. Both require an exact profile and one
server-native Linux image, remain outside an Empirica run, and never pull, build, load, log
in, repair, switch context, or accept model-authored runtime input.

Qualification has five mandatory probes: sandbox realization PASS, natural 125 FAIL,
output overflow unavailable, a qualification-only five-second timeout unavailable, and selected
profile networking. A failed networked `wget` exits 46 and yields `network-egress-unavailable`. OOM qualification is optional, while runtime OOM and exit 137 always remain
unavailable. Every probe uses the production compiler, staging, journal, bounded effects, semantic
admission and exact-ID cleanup path; the networked probe additionally observes sole bridge
membership while the container is running. Candidate construction proves only recorded IDs absent
and journal/staging roots empty, never global Docker census equality.

The legacy environment-readiness helper remains a plugin-process prerequisite, not Docker
capability authority: it accepts canonical executable CPython >=3.10 on supported Darwin or Linux
POSIX hosts, process/session/no-follow capabilities, exact compatible jsonschema version/origin and
Draft 2020-12 APIs, and import-smokes the shipped bridge, protocol and run-state modules at their
exact plugin-root paths. Its Python-byte diagnostic is not included in the `/2` Docker execution
binding. Dependency/API/origin imports run under the same canonical Python in a scrubbed process
group with a 5-second/64-KiB ceiling. Timeout, output overflow, malformed output, or child failure is
a structured unavailable reason and bounded process-group cleanup leaves no descendant. No upper
Python cap is asserted.

After discovery, every qualification and runtime operation uses only the resolved canonical CLI target (an ordinary symlink to that regular executable is accepted) and a closed host environment (`LANG=C`, `LC_ALL=C`, exact local Unix `DOCKER_HOST`, and an
empty profile-owned Docker config directory). A nonempty config refusal identifies the offending private directory without exposing file contents. There is no ambient context, host execution, proxy,
credential, image-acquisition, or network-profile fallback. Runtime selection is read-only;
historical resolution re-observes the exact environment, implementation, Docker, endpoint, and
image identities by digest. A new installed pointer can affect only future runs.

The application accepts only closed single-container `empirica.spike-plan-draft/2` data: one local
image reference, exact argv, optional repository-relative file/directory inputs, and a bounded
environment map. The host resolves immutable image/platform facts, expands one captured input union,
and seals every policy/profile/runtime fact before request CAS. Fixed framework policy owns uid/gid
65534, `/work`, `/tmp`, `/inputs`, `min(2, NCPU)` CPU, 2 GiB memory, 256 PIDs, ulimits, streams,
network profile, and the 120-second workload. Natural 137 and every substrate ambiguity admit no
result. There is no `/1` loader or multi-container author surface.

Production composition loads the passive Docker authority, bounded local-image resolver, and the
single-container `/2` harness lazily. The harness cannot qualify, install, create, or repair authority during ordinary execution; absent, old, malformed,
or drifted authority freezes spikes unavailable before mutation. Separate operator-only Make targets own candidate qualification and installation. No old command-string,
multi-container, qualification-procedure loader, translation, or host fallback is retained.

Timeouts are four distinct limits, not one extensible workload allowance. The container workload hard
limit is 120 seconds. The Docker backend's 210-second whole-operation limit reserves bounded cleanup
and postflight phases after effects. Pi grants only an exact schema-shaped public
`ObserveAction`/`spike_request` a 300-second **outer transport margin**; every near-miss and ordinary
public operation remains at 30 seconds. Claude MCP's 360-second tool ceiling is likewise an outer
transport margin. Neither 300 nor 360 seconds can extend the 120-second workload. The authoritative
`workload_output_limit_bytes` is 1 MiB **per stream**: stdout and stderr are counted and retained
separately, and either stream exceeding its ceiling is output-limited (it is not a 1 MiB aggregate
budget). Workload timeout, output limiting, or OOM is unavailable substrate execution, not a failing
experimental result, and admits no `spike` result evidence.

The generic authority implementation manifest binds every source that selects or resolves authority,
constructs or invokes public `ObserveAction` transport, classifies or enforces that transport's outer deadline,
owns the run repository/CAS that seals request state before execution, or owns the Claude MCP ceiling. It also
binds all seven runtime-loaded vendored v2 JSON documents: public contract and schema, public tool projection,
request and response schemas, host profiles, and persisted-state schema. Root contract duplicates are not
runtime inputs and remain outside the authority; `make vendor-check` owns their byte identity with the vendored
copies. The source set includes the shared bridge, MCP server/public tools, Claude and Codex transports, Pi
translate/index/stdio/process sources, the located repository plus filesystem repository and FS I/O that own the
request-sealing run CAS, and `.mcp.json`, in addition to the generic plan, capture, staging, authority,
effect, journal, harness, and qualification/installer implementation. The two scripts are thin
argument adapters over that bound module. Pi's `private-transport.ts` and `private_bridge.py` cannot carry
public `ObserveAction` requests and retain the ordinary 30-second bound. Claude and Codex public entry adapters
converge on `adapters.bridge.handle`; Pi converges through `adapters/pi/bridge.py` to the same bridge. None owns
or can select a weaker harness.

Empirica 6's public backend projection is covered by `make empirica-run3-check`: both exact closed
RunView/GetArgument shapes, no diagnostic extension, exact host-owned profile selection only at `StartRun`, immutable persisted binding, rejection of every non-run/3 state discriminator without mutation,
and a fresh run/3 generation. The same target binds the agent-visible 120/210/300/360 hierarchy and resource/no-evidence
wording to the sandbox, Pi transport, and Claude MCP constants. `core/projection.py`, `core/observer.py`,
`application/observer.py`, and the UI sources are deliberately outside `IMPLEMENTATION_SOURCE_PATHS`: they display the
already-persisted binding and cannot select, resolve, execute, or admit a harness. The changed runtime-loaded
`vendor/contracts/empirica/v2/public-contract.json` and response/request/public-tools schemas are inside the manifest,
so this public-contract cutover still invalidates every earlier installed qualification. UI contract and fixture copies
are display-only and remain byte-owned by `make contract-fixtures`/`make vendor-contracts`.

Every hermetic test module or shared driver that can reach the production bridge imports
`tests/sandbox_isolation.py` before that bridge. The helper holds a process-lifetime temporary root
and forces `EMPIRICA_SANDBOX_HOME` to an absent child, including in bridge subprocesses, so a
developer's installed qualification authority cannot make direct unittest invocation discover or
execute Docker. Qualification and sandbox-home semantic tests remain excluded because their own
fixtures are the authority under test.

The generic runtime journal is a reconstructing `siffran.empirica.generic-docker-operation/2`
document under exact `generic-runtime-v2`. It binds the current single-container compiler inputs and
operation digest, admits only monotonic lifecycle states, preserves bounded replay and exact resource
sets, revalidates exact container/network authority before conservative cleanup, and stages only the
sealed immutable snapshot. Every transition and exact-ID adoption is atomically replaced and fsynced;
the journal is removed only after exact Docker absence, no-follow staging absence, and postflight
authority equality. Crash-boundary tests recover after every isolated lifecycle transition without a
Docker daemon.

## The one gate: `make verify`

`make verify` (`scripts/verify.py`) is the gate a reviewer or an orchestrator runs before a change is handed over. Its steps are Makefile targets in waves: the installs (`node_modules`, `dev-install`, `ui-install`) side by side; then `release-check`'s own targets (read from its line in the Makefile, so the two cannot drift), `ui-contrast` and `observer-deep` side by side; then the steps that time something (`ui-browser`, `ui-smoke`, `observer-smoke`) one at a time on a quiet machine. Inside a wave a step starts when nothing runs, or while the 1-minute load is under `RUN_SUITES_MAX_LOAD` (default: the CPU count) and fewer than `JOBS` run, as `run_suites.py` admits suites. `dev-install` and `ui-install` are skipped (`skip`) while their lockfile (`requirements-dev.txt`, `plugins/empirica/ui/package-lock.json`) has the SHA-256 they last passed with, recorded inside what they installed (`verify.LOCKS`), so removing `.venv` or `node_modules` installs again. `UI=0` skips `ui-browser` and `ui-smoke`. It prints one line per step as it ends (`verify: NAME ok|FAIL|skip|stopped SECONDS`); at the first failing step it stops the rest of its wave (`stopped`), runs no later wave, prints the failing step's log and exits non-zero naming it; every step's log is kept and its folder printed. A step over its wall limit (`verify.LIMITS`, else 600 s; `--step NAME@SECONDS=...` in its tests) fails as `timed out after N s`; it, the steps stopped beside a failure and whatever a passed step left behind are stopped by the owner the suites use (above), so the suites of a nested `run_suites.py` go with their step. Every step runs under a scratch `HOME`, `EMPIRICA_HOME`, `TMPDIR` and `npm_config_cache` of its own, inside one scratch directory made for the run and removed when it ends, however it ends; Chrome runs with a mock keychain (`ui/tests/cdp.mjs`), so no keychain dialog appears.

**The registry steps keep the real `HOME`.** `node_modules` (`npm ci`), `empirica-subagents-matrix` (`npm install` of each reviewed pi-subagents) and `empirica-pi-api-typecheck` (`npm pack` of each Pi version) are the only steps that install from the npm registry (`verify.REGISTRY`). A user's `npm` may be a firewall shim (Socket Firewall) that reads its configuration, and a CA private key, under the real home, so those three run with the real `HOME`; copying that configuration into a scratch home is ruled out. Their `EMPIRICA_HOME`, `TMPDIR` and npm cache stay scratch, every other step keeps the scratch `HOME`, and npm is whatever `PATH` finds: the firewall is never bypassed. A registry step may write nothing under the real `~/.claude` or `~/.pi`: on macOS it runs under `sandbox-exec` denying those writes (the step fails), elsewhere the two trees are compared before and after it.

No target is listed twice (`check` holds `check-static`: ADRs, docs, contracts, manifests). `ui-contrast` is a step of its own because it is the one check of `ui-build` that neither `release-check` nor `ui-browser` runs; it reads the tokens and rebuilds nothing tracked (`ui-vendor` and `ui-css` rewrite committed files, so they are not steps). `scripts/tests/test_verify.py` (in `suites-check`) holds the order and the waves, the skips (`UI=0`, an unchanged lockfile), steps running side by side, the stop at the first failure (and of the rest of its wave), the scratch home of each step, the registry steps' real home and their denied writes.

`make release-check` deliberately includes the fast gate and the integration diagnostics (core, governance, host, the reviewed pi-subagents matrix and the Pi API typecheck). Release evidence beyond it is the long-running scenarios (`.agents/skills/native-qualification/references/scenarios.md`), which no target runs. It is not the everyday development loop. A matching source revision's completed check is reusable evidence; do not rerun identical bytes merely because the next action is a commit.

The old D-stage aliases and custom v2 preflight runner were removed. Full v2 diagnostics now use ordinary `unittest discover`. Historical ADR/design commands remain historical evidence, not current entrypoints.

## What was subtracted

- The repository-root Pi package no longer reruns the same adapter typecheck and Node suite.
- Repeated Pi simulated end-to-end journeys (`adapter-conformance.test.ts` and `governance-ui.test.ts`) were removed. Their UI-only assertions—strict numeric input, Escape/cancellation, unknown choices, locked confirmation, and safe rendering—live in `governance-ui-unit.test.ts`. Real-service CAS, stale/replay, durable guidance, identity-class, and denial rules remain in Python governance tests; a bounded local bridge smoke remains in the Pi suite.
- The duplicate private transport file was merged into `transport.test.ts`.
- The obsolete v2 `__main__.py --preflight` machinery was deleted; it encoded stale fixed file/test counts and duplicated schema/static checks.
- Scripted online Codex sessions and credential copying were deleted. Deterministic package/hook/MCP tests remain.

This deliberately reduces TS-to-real-Python whole-journey coverage: the remaining service and UI tests are not equivalent proof of native composition. Real activation, dialogs, configuration revocation, audit execution and guarded completion now require the skill-led native scenario. Cheap properties still catch malformed input and authority defects that a single human scenario cannot exhaust.

Contracts and vendor schemas were not deletion candidates. The shared v2 driver/SUT adapter remain because the live behavioral modules import them; removing that seam would be a test architecture rewrite rather than redundant-runner subtraction.

## Inspecting run state

`make empirica-runs` is the read-only census of operational run state (`scripts/empirica_run_census.py`). It enumerates only the documented store layout `<home>/projects/*/runs/*/gen-*/run.json` under `EMPIRICA_HOME` (default `~/.empirica-plugin`), and qualification homes only at `<root>/<candidate>/<cell>/state` via `ARGS="--qualification-root <dir>"`. Use `--runs`, `--status`, `--host`, `--run <id-prefix>` and `--json` through `ARGS`. Host attribution is inferred from the audit role profile and native id and is labelled as such. Do not search for run state with recursive walks over `$HOME`, `/tmp` or worktrees: they traverse `node_modules` and `.git` and take minutes. `make empirica-run-census-unit-check` (part of `check-static`) guards the fixed layout and the no-write property.

`make claude-subagent-models` reports requested versus served models for Claude Code `Agent` launches (`scripts/claude_subagent_models.py`). It joins each parent session under `~/.claude/projects/<project>/<session>.jsonl` with its `subagents/agent-<id>` transcript at fixed depth. Use `ARGS="--agent empirica:empirica-auditor"`, `--requested-only`, explicit session paths or `--json`. Synthetic transcript rows are excluded from served-model output. A concrete served model is identity evidence only when the adapter also correlates it to the verdict-bearing audit child; a requested alias or configured pin is not. `make claude-subagent-models-unit-check` is part of `check-static`.

`make empirica-pi-auditor-resolution [DIR=<project>] [STRICT=1] [PACKAGE_ROOT=<pi-subagents dir>] [SETTINGS=<settings.json>]` reports which auditor file a pi-subagents package resolves for a project in each agent scope (`scripts/pi_auditor_resolution.mjs`), through the package's public `pi-subagents/preflight` export. The package root defaults to the devDependency (a fixture); pass the operator's real install as `PACKAGE_ROOT` to probe what Pi actually runs, and `SETTINGS` to name the Pi `settings.json` (default `$PI_CODING_AGENT_DIR` or `~/.pi/agent`; tests always pass it and never read the home directory). A settings file the package rejects (for example a field it removed) exits 2 with the package's own message. pi-subagents keys agents by name and the runtime's own precedence decides which file wins (at 0.75 a project agent wins over a user-level one); the probe reports that answer rather than restating a rule. Run it with `STRICT=1` before Pi qualification. `make pi-auditor-resolution-unit-check` (part of `check-pi`) runs it in an isolated HOME, including a shadowing negative control.

The adapter classifies every `subagent` call against a reviewed inventory of the owner's exact pi-subagents version (`plugins/empirica/adapters/pi/compat/pi-subagents-<version>.json`, generated — never hand-edited). `make pi-subagents-inventory [PACKAGE_ROOT=...]` regenerates one (it also records the package's declared `@earendil-works/pi-ai` peer as `peer_pi_ai`, from which the README's "Requires Pi" column is derived and checked by `make activation-check`; the devDependency by default; it reads the package's private parameter schema and action list because pi-subagents exports neither — see the script header); the unit check fails if the devDependency's file drifts, and verifies older versions when `PI_SUBAGENTS_ROOTS='{"0.64.0":"<dir>"}'` is set. `make pi-preflight-fixture [PACKAGE_ROOT=...]` re-captures the real preflight responses the admission seam is tested against (`adapters/pi/test/fixtures/preflight-<version>.json`; the `digest` fields hash the capture's scratch paths and differ per capture). A new pi-subagents release is supported only after its inventory and fixture are generated, reviewed, and checked in; until then the owner is refused with `host.subagents_version_unsupported`.

`make empirica-context-economy-report FILE=<slice> [MAX=<chars>]` measures the qualification `context_economy` row reproducibly (`scripts/empirica_context_economy.py`). The measurement object is the model-visible tool result **text** each Empirica tool (`empirica_read`, `empirica_observe`, `report_convergence`) returns to the model — the host `content` text — counted in Unicode code points; the interval is the primary run from activation to terminal; only Empirica tools count. The operator extracts the ordered tool results from the retained transcript/log into a newline-delimited JSON slice (one `{"tool": ..., "result": {"content": [{"type": "text", "text": ...}], ...}}` per call). The counter consumes the rendered text as-is (it never JSON-decodes that text), reports the maximum
single and total model-visible characters and, tracked **separately** in UTF-8 bytes, the text-only
transport envelope size. Claude/Codex MCP results contain no duplicate RunView
`structuredContent`; Pi's validated JSON remains host-internal `details`. `MAX=<chars>` fails when
any single result exceeds that ceiling. Empirica 6's mirrored Python/Pi post-mediation author-view regression uses a
strict `<1300` ceiling; the largest measured case is the unavailable-backend configure dismissal at 1257 UTF-8 bytes,
leaving 43 bytes while retaining the exact no-spike/research/graph/honest-stop guidance. `make
empirica-context-economy-unit-check` (part of
`check-static`) guards the counter's fixed layout and no-write property.

## Native logs

For Claude qualification, launch with `make claude-dev CLAUDE=/absolute/supported/claude ARGS="--debug-file /absolute/evidence/claude.debug.log"`, then validate that retained admission log with `make empirica-claude-mcp-log-check LOG=/absolute/evidence/claude.debug.log`; optional expectations belong in `ARGS` as shown by `make help`. Launch Pi with `make pi-dev PI=/absolute/supported/pi`.

## Host version ranges

Pi's range (`host-profiles.json` `compatibility`, `>=1.0.0,<2.0.0`) is enforced at `/empirica` start by `checkHostVersion` (`adapters/pi/src/host-profile.ts`): outside it, or with an unreadable version, nothing starts (`host.version_unsupported`; stderr and exit 1 without a UI). It is tested by the `INVARIANT (G19b)` test in `adapters/pi/test/gate.test.ts`. Claude Code's range is the documented supported range and is not checked, because hook payloads carry no version; Claude is admitted by observed capability. The pi-subagents range is enforced at runtime (`make empirica-subagents-matrix` proves the reviewed versions).

## Native qualification

`make native-qualification` prints the path to `.agents/skills/native-qualification/SKILL.md` (the portable Agent Skills directory; `.claude/skills/native-qualification` is a relative symlink to it); it launches nothing. The skill specifies `make claude-dev` (directory plugins) and `make pi-dev` (project package override); neither changes the global installation. Follow the skill in an explicitly authorized, operator-present session using a supported Claude or Pi environment; the human supplies every consent response. Codex Empirica can establish only its expected refusal. Partial and failed evidence belongs in the skill's checkpoint ledger.
